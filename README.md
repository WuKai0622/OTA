# STM32F407 三通道远程固件升级（OTA / IAP）系统

一套完整的**嵌入式远程升级系统**：自绘 STM32F407 板上的 Bootloader + 被测应用固件 + ESP32-C3 WiFi 桥 + PC 上位机。

**不拆机、可远程、任意时刻断电都不会变砖。**

## 这个仓库里有什么

```
OTA/
├── bootloader/          F407 引导程序（Keil MDK 工程）+ PC 上位机工具
│   ├── Core/                自研核心：环形缓冲、帧协议、跳转、A/B 决策
│   ├── LWIP/                lwIP 移植层（含零拷贝以太网驱动）
│   ├── Drivers/ Middlewares/  HAL / CMSIS / lwIP 源码
│   ├── MDK-ARM/             Keil 工程（编译产物已 gitignore）
│   ├── tools/               ★ PC 上位机：PySide6 图形界面 + 无界面 CLI
│   └── README.md            ★ bootloader 详细说明（架构、协议、分区、设计点）
│
├── app/                 被测应用固件（FreeRTOS，用来验证升级真的生效）
│   ├── v1.0/                LCD 显示 "APP1.0 running..."
│   └── v1.1/                LCD 显示 "APP1.1 running..."（带颜色）
│
└── esp32/wifi/          ESP32-C3 的 SPI ↔ TCP 桥（ESP-IDF 工程）
    └── main/                WiFi 连接 + SPI 从机 + TCP 服务器
```

四部分的分工：

| 部分 | 跑在哪 | 作用 |
|---|---|---|
| **bootloader** | STM32F407 | 上电先跑它。收固件、写 Flash、校验、跳转到应用；**永远不擦除自己** |
| **app v1.0 / v1.1** | STM32F407 | 被测的应用固件。**两份只差 LCD 上显示的一行字** —— 升级完看一眼屏就知道换没换成 |
| **esp32/wifi** | ESP32-C3 | 一条**与内容完全无关**的字节管道：把 SPI 收到的字节灌进 TCP，反之亦然 |
| **tools** | PC | 把固件切成帧推下去，逐帧等 ACK，失败重发 |

> **为什么 app 只需要两份差一行字？** 因为验证升级这件事，要看的不是"固件变复杂了"，而是"**板子上跑的确实是新固件**"。
> 一行版本号字符串就是最直接、最不可能被误判的证据 —— 屏上从 `APP1.0` 变成 `APP1.1`，升级就是真的成了。

## Flash 分区

STM32F407ZGT6 有 1MB Flash，按扇区切成这样：

| 区域 | 起始地址 | 扇区 | 大小 | 作用 |
|---|---|---|---|---|
| **bootloader** | `0x08000000` | S0–S4 | 128 KB | 引导程序，**永不擦除** |
| **参数区** | `0x08020000` | S5 | 128 KB | 32 字节升级记录（版本号/长度/健康标志） |
| **运行区 run** | `0x08040000` | S6 | 128 KB | 当前正在运行的固件 |
| **下载区 A** | `0x08060000` | S7 | 128 KB | 新固件的落地区 |
| **备份区 B** | `0x08080000` | S8 | 128 KB | 上一个**已知好用**的固件（保命用） |
| 保留 | `0x080A0000` | S9–S11 | 384 KB | 预留 |

> ⚠️ **两个分区设计上的细节，都是被坑出来的：**
>
> - **参数区为什么在 `0x08020000` 而不是 `0x08010000`？**
>   bootloader 镜像实测 77KB，代码一直铺到 `0x08013493`。参数区若放在 `0x08010000`，
>   第一次写记录时擦除 S4 就会**把 bootloader 自己擦掉** —— 症状是"上位机报升级成功，随后卡在 `DL:`，重启黑屏"。
>
> - **下载区为什么恰好是一个扇区？**
>   F407 单 bank，最小擦除单位就是扇区，而 S7 正好 128KB = `APP_MAX_SIZE`。
>   所以"擦下载区"就是**擦一个扇区**，不会跨越扇区边界。

**掉电保护靠 A/B 双分区 + 健康标志**：新固件先落到 A 区 → 校验 → 拷进运行区**试运行** →
应用自己稳定跑 2 秒后往参数区写一个健康字 → **下次复位时** bootloader 看到健康字才把它固化成新的 B 区。
如果新固件根本跑不起来（连健康字都来不及写），下次复位自动从 B 区恢复旧版本。

## 三条升级通道

三条链路**共用同一套帧协议**，上位机只需切换传输层。

| # | 通道 | F407 侧 | 对端 | 说明 |
|---|---|---|---|---|
| ① | **以太网** | `ota_net.c`，TCP **服务器** `192.168.1.2:5001` | PC 直连 | 最快，免配对 |
| ② | **蓝牙** | USART3 空闲中断 | HC-05 透传 | 免布线，笔记本/手机就地升级 |
| ③ | **WiFi** | `ota_spi.c`，SPI2 **主机** | ESP32-C3 → WiFi → PC | 彻底无线 |

### 通道③ 为什么值得单独说

ESP32-C3 **完全不知道 OTA 这件事**。它只是一条字节管道：

```
PC ←──WiFi/TCP:5001──→ ESP32-C3 ←──SPI 全双工──→ F407
```

F407 那头从"回显自检"换成"真 OTA"时，**C3 侧一行代码都没改**。
这是刻意设计的结果：先把"透传"单独验通，再接真协议 —— 接 OTA 时若出问题，只剩下"帧协议/会话绑定"两个变量，
不会再混进"SPI 通不通""TCP 通不通"。

三种"不主动问就没有数据"的差异也集中在这条通道上：**SPI 的时钟是主机（F407）发的**，
所以 bootloader 必须在主循环里周期性调用 `OTA_Spi_Poll()` —— 少了它，走 WiFi 的升级会在
5 秒等待窗口过后彻底静默（PC 看到的就是"START 之后没下文了"）。

## 硬件接线

### 以太网（通道①）

| F407 | LAN8720A | 说明 |
|---|---|---|
| PA1 | REF_CLK | RMII 50MHz 参考时钟 |
| PA2 | MDIO | 管理接口数据 |
| PA7 | CRS_DV | 载波侦听 / 数据有效 |
| PC1 | MDC | 管理接口时钟 |
| PC4 / PC5 | RXD0 / RXD1 | 接收数据 |
| PG13 / PG14 | TXD0 / TXD1 | 发送数据 |
| PG11 | TX_EN | 发送使能 |
| — | PHY 地址 | **LAN8720A**，与 LAN8742A 寄存器兼容 |

> 注：CubeMX 生成的 PHY 驱动目录叫 `Drivers/BSP/Components/lan8742/`，那是 ST 模板的默认命名
> （取自 ST 自家评估板），**不代表实际芯片型号**。

### 蓝牙（通道②）

| F407 | HC-05 |
|---|---|
| PB10 | USART3_TX → RXD |
| PB11 | USART3_RX ← TXD |

**19200 8N1**（弱链路下主动降速换稳定性）。

### SPI / WiFi（通道③）

| F407（主机） | ESP32-C3（从机） | 信号 |
|---|---|---|
| PB13 | GPIO6 | SCK ← 时钟由 **F407 发** |
| PC3 | GPIO7 | MOSI |
| PC2 | GPIO5 | MISO |
| PB12 | GPIO10 | CS（F407 软件片选，拉低即开始一笔事务） |

> ⚠️ **两块板必须共地。**
> C3 的 MISO 之所以不用 GPIO2（那才是 FSPI 的 IO_MUX 默认脚，走 IO_MUX 更快）——
> 因为 **GPIO2 是 C3 的 strapping 脚，上电时必须为高**，挂上 SPI 从机的输出有风险。
> 改用 GPIO5 由 GPIO 矩阵路由，代价可忽略，换来启动可靠性。

通信参数：**Mode 0**（CPOL=0 / CPHA=0）、8 bit、MSB first、全双工、软件 NSS、预分频 /32（**1.3125 MHz**）。
起步必须慢 —— 杜邦线没有地平面，快了必然振铃。**先求通，再求快。**

> ⚠️ **供电：共源、不共轨 —— 两边的 3V3 不要连。**
> 用一个电源供两块板，各走**独立的一对 VCC/GND**。这是上板实测的最终结论，中间改过两次：
>
> 1. 两块板各用各的供电来源、只靠一根细地线相连 —— **不够**。两个来源各有各的地参考，
>    WiFi 的脉冲回流叠上两边均流全挤在那根线上，地弹跳被打进 SPI 的判决电平。
>    表现是**间歇性坏帧**，但 **TCP 连接全程没断** ⇒ 是信号被打坏、不是芯片复位。
> 2. 于是试过把两边 3V3 也直连 —— 坏帧压住了，但 **F407 的 3V3 轨变成由 C3 的稳压器一起供着，LCD 狂闪**。
>    屏能被电源波动刷到肉眼可见，说明轨在动的量级是**几百 mV**，足以打坏 3.3V 的 SPI 边沿 ——
>    **屏闪和丢帧是同一个根因的两个表现，屏是那个看得见的金丝雀。**
> 3. 最终：一个电源供两块板、各走独立的一对线，3V3 不连 —— 升级成功且不再闪。

## 快速开始：跑通一次完整升级

### 第 1 步：编译并烧录 bootloader

```
用 Keil MDK 打开 bootloader/MDK-ARM/OTA_ETH.uvprojx，编译，SWD 下载
```

确认链接地址：**IROM1 = `0x08000000`，Size = `0x20000`（128KB）**。
跑起来后 LCD 显示 `Wait OTA: 5` 倒计时。

### 第 2 步：准备应用固件

`app/v1.0` 和 `app/v1.1` 各自用 Keil 打开编译，各得到一个 `.bin`：

| 工程 | 链接地址 | 产物 |
|---|---|---|
| `app/v1.0/MDK-ARM/OTA_test_F407.uvprojx` | `0x08040000`，Size `0x20000` | `MDK-ARM/SLOTA_test_F407.bin`（约 26 KB） |
| `app/v1.1/MDK-ARM/OTA_test_F407.uvprojx` | `0x08040000`，Size `0x20000` | `MDK-ARM/SLOTA_test_F407.bin`（约 26 KB） |

> ⚠️ 编译产物默认被 `.gitignore` 排除，**克隆仓库后需要自己编译**才能得到 `.bin`。

**第一次上电**：可以先 SWD 把 `app/v1.0` 直接烧到 `0x08040000` 作为"出厂固件"，
然后就能通过 OTA 升到 v1.1 —— 这样才是完整的演示。

### 第 3 步：编译 ESP32-C3 桥（走 WiFi 才需要）

```bash
cd esp32/wifi
idf.py set-target esp32c3
idf.py build flash monitor
```

默认 **AP 模式**（考场/现场不一定有可用路由器，AP 模式完全不依赖外部网络）：

- 热点 SSID：`OTA_ESP32`，密码：`12345678`
- 拿到 IP：**`192.168.4.1`**，TCP 端口 **5001**

> 想连现有路由器就把 `main/wifi_link.h` 里的 `WIFI_USE_AP` 改成 `0`，
> 并填上 `WIFI_STA_SSID` / `WIFI_STA_PASS`，然后重新编译烧录。

> ⚠️ **上电顺序：先给 ESP32 上电（或复位），再复位 F407。**
> F407 的 bootloader 只有 **5 秒**等待窗口，而 C3 的 WiFi 连接 + DHCP 要 2~5 秒。
> 反过来的话窗口期可能赶不上，PC 连上来时 boot 已经去跳应用了。

### 第 4 步：推送固件

```bash
# ① 以太网通道（推荐，最快）
py bootloader/tools/ota_host.py --tcp 192.168.1.2:5001 app/v1.1/MDK-ARM/SLOTA_test_F407.bin

# ② 蓝牙通道（COM 口为 HC-05 配对后的 SPP 虚拟串口）
py bootloader/tools/ota_host.py COM5 app/v1.1/MDK-ARM/SLOTA_test_F407.bin --baud 19200

# ③ WiFi 通道（先让 PC 连上 OTA_ESP32 热点）
py bootloader/tools/ota_host.py --tcp 192.168.4.1:5001 app/v1.1/MDK-ARM/SLOTA_test_F407.bin
```

或者用图形界面：

```bash
py bootloader/tools/host_qt/main.py
```

### 第 5 步：看结果

升级成功后 LCD 上的字从 `APP1.0 running...` 变成 **`APP1.1 running...`（带颜色）**。
上位机侧打印：

```
[4/4] 结果: 成功  (帧数=78, 消息=OTA_END ACK=OK)
      升级耗时: 1.27 秒  = 擦除下载区 1.03 + 传输 0.24
      传输段吞吐: 879.9 kbps (107.4 KB/s, 每帧 9.0 ms)
      含擦除总吞吐: 167.9 kbps (20.49 KB/s)
```

## 关键设计

### 1. 三通道收敛到一个环形缓冲

```
                    ┌──────────────┐
   HC-05 蓝牙 ──────►│  USART3 中断 │──┐
                    └──────────────┘  │
                    ┌──────────────┐  │   临界区保护
   以太网 TCP ──────►│ lwIP 主循环  │──┼──► 同一个 8KB 环形缓冲 ──► Proto_Feed()
                    │   轮询       │  │       （单一帧状态机）
                    └──────────────┘  │
                    ┌──────────────┐  │
   ESP32-C3 ────────►│ SPI2 主循环  │──┘
                    └──────────────┘
```

环形缓冲是**三条通道唯一的汇合点**。三个驱动唯一的区别，就是写环时声明的那一个通道号。
于是帧状态机、命令分发、Flash 写入路径全部只有**一份**。

生产者有两个（USART3 中断 + 主循环里的 ETH/SPI 回调），会互相打断，所以写环进临界区。
临界区最长就是 len 字节的拷贝（8KB 全拷也仅数十微秒 @168MHz），对中断延迟影响可忽略。

### 2. 会话绑定：ACK 永远不会发错通道

收到 `CMD_OTA_START` 时**锁存**发起通道：

```c
g_sess_chan = g_cur_ch;    /* ★ 在参数校验【之前】锁存 */
```

发送时统一走 `TxChan()` 选路。两个细节都是必需的：

- **为什么校验之前就锁存** —— START 参数非法时也要回一个 ERR ACK，而那个 ACK 同样得发回**发起方**通道。
- **为什么不能"发送时刻看哪条通"** —— 加 SPI 通道之前，选路逻辑是"TCP 通则走网口，否则走串口"。
  三条通道都通了之后这个判据就**错了**：PC 完全可能挂着一条**闲置的 ETH 连接**而升级走 WiFi，
  于是 ACK 被发去 ETH，PC 在 SPI 侧永远等不到应答。

### 3. 逐帧停等 + 幂等重传

每个数据帧必须等 ACK 才发下一帧，帧里带起始偏移。好处：

- bootloader 侧**不需要任何乱序重排逻辑**（帧按偏移顺序到达）
- **重传天然幂等** —— `off + n <= 已确认总量` 就直接回 ACK 而不重写 Flash

丢帧的兜底不在 bootloader 里，而是**上位机超时重发**，两端职责不重叠。

### 4. 以太网零拷贝接收

```c
typedef struct {
    struct pbuf_custom pbuf_custom;               /* 前部：lwIP 的 pbuf 结构 */
    uint8_t buff[(ETH_RX_BUF_SIZE+31) & ~31] __ALIGNED(32);  /* 后部：DMA 缓冲 */
} RxBuff_t;

LWIP_MEMPOOL_DECLARE(RX_POOL, 12U, sizeof(RxBuff_t), ...);   /* 12 个预分配 */
```

ETH DMA **直接写进 pbuf 的缓冲**，从网线到协议层一次 `memcpy` 都没有。

### 5. 跳转前的九步收尾

裸机跳转的顺序一步都不能错：

```
① OTA_Net_DeInit()    ← 必须在关中断之前：ETH DMA 是总线主设备，
                        不先停掉它，app 跑起来后它还会继续写 boot 留下的描述符环
② OTA_Spi_FlushTx()   ← 队列销毁前把最后的 ACK 推上总线
③ OTA_Spi_DeInit()
④ __disable_irq()
⑤ 清 NVIC ICER / ICPR  ← 防 boot 期间的挂起中断在 app 里误入
⑥ 停 SysTick
⑦ SCB->VTOR = 运行区地址
⑧ __set_MSP(新栈顶)
⑨ app_entry()
```

## 实测数据

在自绘 F407 板 + PC 网线直连（**10M 半双工**）环境下实测，固件 26 KB：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| **擦除下载区** | **1.03 s** | ⚠️ **固定成本** |
| 传输 78 帧 | 0.24 s | → **879.9 kbps**（每帧 9.0 ms） |
| **合计** | **1.27 s** | 含擦除总吞吐 167.9 kbps（20.49 KB/s） |

> **为什么擦除是固定成本、且无法优化？**
>
> 1. **不能擦更少** —— F407 单 bank，最小擦除单位就是 128KB 扇区，而下载区正好是一个完整扇区。
>    ST 规格：128KB 扇区擦除**典型 1s、最坏 4s**，与固件大小完全无关。
> 2. **不能和传输重叠** —— 单 bank 的 F407 在擦除期间 Flash 总线停摆，连 CPU 取指都取不了
>    （bootloader 自己的代码就跑在 Flash 里）。即使做到完美重叠，最多也只省下 0.24 s。
>
> **所以"总吞吐"不是链路能力指标**：同一块板子传 26KB 时约 168 kbps、传 79KB 时约 497 kbps，
> 差异全来自那个固定的 1.03 s。**要看链路能力得看"传输段吞吐" = 879.9 kbps。**
>
> 至于 879.9 kbps 只占 10M 链路的 8.8% —— 那 91% 的空闲花在**逐帧停等的往返开销**上
> （每帧 9.0 ms 里只有约 0.85 ms 真正在走线缆）。改成滑动窗口需要动 bootloader 协议、
> 而收益上限只有 0.24 s，**不值得**。

## 已知限制

本项目定位是**单机位、有人值守的现场升级工具**，以下限制是有意接受的取舍：

- **无看门狗** —— 擦除 Flash 期间 CPU 停摆，硬件看门狗会误复位。代价是 boot 卡死时没有自动恢复手段。
- **同一时刻只支持一条通道升级** —— 环形缓冲只存字节、不存来源，用"最后写入者"近似。
  前提是其余通道空闲（不产生字节）。真需要双通道并发，正确做法是**给环加逐段来源标注**，
  而不是在现有逻辑上打补丁。
- **MAC 地址写死为 `00:80:E1:00:00:00`** —— 直连场景够用，但同网段放两块板会冲突。
- **无加密与签名验证** —— 固件不带签名，能连上就能刷。生产环境需要补固件签名校验。
- **单机位** —— 没有并发升级、没有设备管理、没有版本服务器。
